# Anki Lite — Improvements Spec (for Claude Code)

> Формат: рабочее задание для агента. Каждая задача самодостаточна — goal, файлы, шаги, acceptance criteria. Реверс-канал реализуется на gRPC (обратный контракт Python→Go), не на HTTP.

> **Архитектурная поправка (2026-07-23):** ниже в CONTEXT упоминаются `auth-service`/`learn-service` как отдельные сервисы. В реальности это один Go-монолит `back/` (один процесс `back/cmd/server`, один Postgres `ankis-db`) — auth и learning просто пакеты (`back/internal/auth`, `back/internal/api` и т.д.), не отдельные деплойменты. Везде далее, где встречается «learn-service»/«auth-service», читать как «`back/`» (или его конкретный пакет). Также Task 7.4 (Curriculum Planner, `curriculum.py`) — этот файл удалён из `ankis/llm/` при чистке 2026-07-22/23 (жив только в отдельном репо `adaptive-learning-repetitor`); проверять нужно, не занял ли его место rule-based `llm/src/adaptive/engine.py`.

---

## GOAL

Довести Anki Lite до продакшн-качества:
0. **Verify core** — убедиться, что адаптивное ядро (BKT, забывание, SRS, планировщик) реально работает end-to-end.
1. **Безопасность чата** — нецелевые запросы и промпт-инъекции не доходят до LLM.
2. **AI-инструменты** — агент умеет читать данные студента и писать в его словарь/тренировку.
3. **Гостевой доступ** — вход без регистрации с сохранением личности между сессиями.
4. **Мобильная адаптация** — полноценная работа на iOS Safari и Android Chrome.
5. **Скорость AI** — измерить и снизить латентность ответа без потери качества.

## CONTEXT

- **Backend:** Go (Gin), микросервисы — `auth-service`, `learn-service`, каждый со своим PostgreSQL. *(См. поправку выше — по факту единый монолит `back/`.)*
- **AI-service:** Python (FastAPI + LangGraph), корпуса в PostgreSQL + pgvector.
- **Связь:** `learn-service` → `llm-service` по gRPC (`tutor.proto`). Поток строго однонаправленный: Go зовёт Python.
- **Агент:** граф `prepare → classify → route → call_model ⇄ tools`. Классификатор намерений — `intent.py`. Роутер — `rag_router.py`.
- **Frontend:** SPA (vanilla JS) + React-лендинг.

## GLOBAL CONSTRAINTS

- Не ломать существующие сценарии: тренировка, чтение, статистика работают автономно от AI.
- Каждую задачу — отдельным коммитом/PR. Не смешивать безопасность, tools и мобилку.
- Перед правкой `intent.py` / `rag_router.py` — прочитать их целиком, не менять по догадке.
- Все новые gRPC-методы — обратно совместимы, старые не трогать.
- Тесты: каждая задача с логикой сопровождается тестом (unit или integration).

### Task 1.2 — Block `off_topic` before LLM

**Goal:** при `off_topic` до модели и RAG дело не доходит, возвращается вежливый отказ.

**Files:** `rag_router.py` (или узел графа, обрабатывающий intent).

**Steps:**
1. Прочитать текущую логику маршрутизации по intent.
2. Добавить проверку **самой первой**, до любого вызова LLM/RAG:
   ```python
   if intent == "off_topic":
       return refusal_message  # LLM и retrievers не вызываются
   ```
3. Текст отказа: вежливый, предлагает задать вопрос по английскому.

**Статус (2026-07-24): РЕАЛИЗОВАНО и проверено end-to-end, не только логически.** Реальная сложность оказалась не в `rag_router.py` (там просто добавить приоритетную ветку), а в том, что граф (`chat/graph.py`) до этого не умел завершаться без узла `model` — нужно было провести это через весь стриминг-пайплайн, не через догадку:
- `RouteDecision` получил `mode="refuse"` + поле `message`; `resolve_route` проверяет `intent=="off_topic"` **первым же условием**, раньше даже forced-действий Adaptive Engine.
- В граф добавлен узел `refuse` и условное ребро `classify → route | refuse` (вместо жёсткого `classify → route`); `refuse` никогда не вызывает `_llm_with_tools` и не создаёт ретриверов — физически невозможно дойти до LLM/RAG в этой ветке.
- Проблема, которую пришлось решать вручную (не тривиально): узел `refuse` не вызывает модель → `on_chat_model_stream`/`on_chat_model_end` никогда не срабатывают → без доп. работы текст отказа НЕ дошёл бы до фронтенда по SSE (`chat/streaming.py::normalize_agent_events` слушает только эти events). Решение — `get_stream_writer()` внутри `refuse` + `stream_mode="custom"` в `graph.astream_events(...)`, событие подхватывается в `streaming.py` как `on_chain_stream`/`name=="LangGraph"`/`chunk.type=="refusal"` и превращается в обычный `ContentEvent`. Это было эмпирически проверено вручную в venv проекта (три отдельных прогона на минимальных графах), а не взято по памяти о LangGraph API — поведение `astream_events`+`get_stream_writer` недостаточно документировано, чтобы доверять этому вслепую.
- `llm/tests/unit/test_graph_refusal.py` — два теста на реальном собранном графе (LLM и БД замоканы): (1) off_topic доходит до `refuse`, `on_chat_model_start/stream` НЕ появляются, кастомный чанк с текстом отказа появляется ровно один раз; (2) regression-тест — обычное сообщение `chat`-intent по-прежнему доходит до модели (защита от того, что новое условное ребро сломает основной путь). Оба теста проходят.

**Acceptance:**
- [x] При `off_topic` LLM не вызывается (проверить, что нет обращения к модели). *(подтверждено эмпирически — см. статус)*
- [x] Возвращается заготовленный отказ.
- [x] Тест `resolve_route` с `intent="off_topic"` → отказ, без вызова retrievers — `llm/tests/unit/test_rag_router.py` (7 тестов, все проходят).

## EPIC 2 — Reverse Channel Python→Go (gRPC) (P1)

> Предусловие для всех пишущих tools (Epic 4). Реализуется один раз.

### Task 2.1 — Define reverse gRPC service

**Goal:** Go-сервис поднимает gRPC-сервер, который вызывает Python; для обратной записи Python вызывает Go по НОВОМУ gRPC-контракту.

Здесь два варианта топологии — выбрать при реализации, по умолчанию **B**:

- **A. Bidirectional** — `learn-service` дополнительно поднимает gRPC-**сервер** (`LearnWriteService`), который `llm-service` дёргает как клиент.
- **B. Callback в рамках стрима** — расширить существующий стрим-контракт: агент шлёт `ToolCall`-события, Go их исполняет и возвращает результат в тот же стрим. Не нужен второй сокет, всё в одном соединении.

**Files:** `proto/` (новый сервис или расширение существующего), кодоген Go+Python.

**Steps (для варианта B — рекомендуемый):**
1. В `tutor.proto` расширить `ChatEvent` / ответный поток типом `tool_call`:
   ```proto
   message ToolCall {
     string tool = 1;          // add_words, delete_word, start_practice ...
     string args_json = 2;     // аргументы инструмента
     string call_id = 3;
   }
   message ToolResult {
     string call_id = 1;
     bool   ok = 2;
     string result_json = 3;
     string error = 4;
   }
   ```
2. `llm-service`: когда агент вызывает пишущий tool — эмитит `ToolCall` в стрим, ждёт `ToolResult`.
3. `learn-service`: получив `ToolCall`, исполняет соответствующую ручку от имени текущего пользователя (user_id уже в контексте стрима), возвращает `ToolResult`.

**Steps (для варианта A):**
1. Новый proto `LearnWriteService` с методами `AddWords`, `DeleteWord`, `StartPractice`.
2. `learn-service` реализует сервер, `llm-service` — клиент.
3. Пробросить токен/`user_id` текущей сессии из входящего gRPC-контекста в исходящий вызов.

**Acceptance:**
- [ ] Python может инициировать запись в Go в рамках обработки одного запроса пользователя.
- [ ] `user_id`/сессия корректно пробрасывается — запись идёт в словарь именно текущего пользователя.
- [ ] При недоступности Go — агент возвращает понятную ошибку, не падает.
- [ ] Integration-тест: Python вызывает reverse-метод → запись появляется в learn-db.

## EPIC 5 — Guest Auth (P0)

### Task 5.1 — Guest login with persistent cookie

**Goal:** вход без регистрации, личность сохраняется между сессиями.
**Files:** `auth-service`, фронт (инициализация сессии).
**Steps:**
1. При первом заходе без токена — сгенерировать гостевой `user_id`, выдать persistent cookie (не session-cookie, долгий Max-Age).
2. При повторном заходе — узнать гостя по cookie, поднять его данные.
3. Проверить поведение на iOS Safari (ограничения на cookie/ITP).
4. (Опц.) Возможность привязать гостя к полному аккаунту позже.
**Acceptance:**
- [x] Гость закрыл вкладку и вернулся — словарь и прогресс на месте. *(подтверждено integration-тестом)*
- [~] Работает на iOS Safari и Android Chrome. *(архитектурно рассчитано на ITP — см. статус; на реальном устройстве НЕ проверялось, честно отмечаю)*
- [x] Cookie переживает перезапуск браузера. *(HttpOnly + Max-Age=400 дней; переживает restart браузера, но не переживает выход из localStorage-токена — это ожидаемо, см. статус)*
- [x] Integration-тест: создание гостя → запись данных → повторный вход → данные те же — `back/internal/api/guest_auth_test.go`, 2 теста, оба проходят против реальной Postgres.

**Статус (2026-07-24): РЕАЛИЗОВАНО, monolith = "auth-service" (см. поправку в начале файла).** Ключевое архитектурное решение — два разных токена, а не один:
- **Сессионный JWT** (`auth.GenerateToken`, TTL 30 дней, как и раньше) — уходит в тело ответа, фронт кладёт в `localStorage`, шлёт как `Authorization: Bearer` на каждый запрос. Не менялся для обычных пользователей.
- **Гостевой device-токен** (`auth.GenerateGuestDeviceToken`, новый, TTL 400 дней — жёсткий потолок самого Safari на срок жизни ЛЮБОЙ cookie, дальше просить бессмысленно) — уходит ТОЛЬКО в `HttpOnly`-cookie `anki_guest_device`, никогда не светится в JS и не используется как Bearer-токен. Единственная цель — пережить возврат гостя через недели/месяцы, когда 30-дневный сессионный JWT в localStorage уже истёк или был вычищен.
  - Если бы использовался один и тот же токен и для cookie, и для сессии, разрыв больше 30 дней означал бы, что при возврате `/auth/guest` не смог бы провалидировать протухший JWT и создал бы НОВОГО гостя, теряя весь прогресс — именно этого паттерна и надо было избежать.
- `POST /auth/guest` (публичный роут, без `RequireAuth`): если есть валидная `anki_guest_device`-cookie — поднимает ТОГО ЖЕ гостя и выписывает свежую сессию (sliding expiration на cookie); если нет — создаёт нового гостя (уникальный `guest-<hex>@guest.local`, случайный пароль, никогда не используется для логина) с тем же стартовым набором из 10 слов, что и обычная регистрация.
- `Logout` теперь дополнительно чистит `anki_guest_device`-cookie — без этого гость, явно вышедший из аккаунта, при возврате тут же тихо залогинился бы обратно тем же гостем (нашёл и исправил это до того, как это стало багом в проде).
- `users.is_guest boolean` — новая колонка (`00007_guest_users.sql`), возвращается в `/auth/me` и в ответе `/auth/guest`.
- Фронт (`front/web/app.js::bootstrap`): по решению пользователя — **полностью автоматически**, без кнопки «продолжить как гость». Если в `localStorage` нет токена, тихо дёргает `/auth/guest` (cookie шлётся браузером сама, same-origin — `fetch` включает credentials по умолчанию, доп. настройки не потребовались) и только при его неудаче показывает обычный экран логина.
- **iOS Safari / ITP — архитектурно, но не проверено на устройстве.** Cookie ставится через `Set-Cookie` с сервера (не `document.cookie` из JS) и помечена `HttpOnly` — именно JS-writable storage (localStorage, `document.cookie`) подпадает под 7-дневную эвикцию Safari ITP, а не серверные HttpOnly-cookie того же first-party домена (Anki Lite отдаёт front+back с одного origin, без CORS). Это должно решать именно ту проблему, ради которой в задаче явно требовалась cookie, а не просто localStorage — но это утверждение НЕ подтверждено реальным прогоном на iPhone/Safari в этой сессии (недоступно в среде выполнения); стоит проверить на реальном устройстве перед тем, как полагаться на этот тезис на защите.
- Опциональный пункт 4 спеки («привязать гостя к полному аккаунту позже») **сознательно не реализован** — помечен как опциональный в самой задаче, отдельная функциональность слияния данных.

### Task 6.2 — Chat scroll to start of answer (P1)

**Goal:** при ответе AI чат скроллится к началу ответа, не к концу.
**Acceptance:**
- [x] При получении ответа виден его верх (первая строка). *(проверено — см. статус, включая скриншот)*

**Статус (2026-07-24): РЕАЛИЗОВАНО и проверено без реального LLM** (через прямой вызов `renderChatMessages`/`state` в браузере — не нужен живой AI, чтобы проверить именно логику скролла).

Причина бага: `renderChatMessages()` (`front/web/app.js`) при **каждом** вызове безусловно делал `box.scrollTop = box.scrollHeight` — а при стриминге ответа она вызывается на каждый content-чанк (`chat/streaming.py` шлёт их по одному слову/фразе). Длинный ответ — это десятки вызовов, и на каждом view предзвно вниз, к текущему хвосту, поэтому пользователь физически не мог увидеть начало ответа, пока стриминг не закончится.

Правка: `renderChatMessages(opts)` теперь понимает два режима:
- `scrollToLastMessageTop: true` — при появлении НОВОГО сообщения ассистента (пустой плейсхолдер прямо перед началом стрима) скроллит так, чтобы был виден верх этого сообщения.
- `preserveScroll: true` — при каждом последующем чанке (тот же текст, просто растёт) сохраняет ту же позицию скролла, не дёргая её к низу.
- Без опций (по умолчанию) — старое поведение (скролл в самый низ), не тронуто для открытия виджета чата, стыковки в practice-экран, готовых (не стримящихся) сообщений типа квиза по теории — там скролл-в-конец уместен и был не при чём к этому багу.

Проверено Playwright-скриптом: напрямую (без сети/LLM) насимулировал 6 пар история + новый вопрос + 40 «чанков» стриминга через реальные `state`/`renderChatMessages` страницы — `scrollTop` не менялся все 40 итераций (не «убегал» к низу), первая строка ответа оставалась в видимой области на протяжении всего процесса. Скриншот подтверждает: видно и вопрос пользователя, и начало ответа одновременно.

**Известный нюанс (не бага, а edge case, оставлен как есть):** если новое сообщение стартует, когда истории мало (`scrollHeight` едва больше высоты виджета), браузер физически не даёт проскроллить до желаемой позиции (нечего скроллить) — верх ответа в этом случае оказывается ближе к низу видимой области, чем в «богатой» истории, но остаётся видимым (проверено — не нарушает акцептанс). Разбирался, стоит ли досогласовывать это через повторный `scrollToLastMessageTop` на каждый чанк вместо `preserveScroll` — отказался: это заставило бы скролл **дёргаться и бороться с ручной прокруткой пользователя** во время чтения длинного ответа, что хуже исходного бага. Не стал городить эвристику «не мешать пользователю, если он сам скроллил» без возможности проверить её на реальном человеке.

- [x] Приоритет — темы, к которым студент готов.
- [ ] Тест на корректный порядок для графа тем.

**Статус (2026-07-23): standalone-планировщика НЕТ в этом репо, но его роль реально исполняет `adaptive/engine.py`.** `llm/src/adaptive/curriculum.py` удалён при чистке 2026-07-22/23 (в файловом дереве `adaptive/` сейчас только `engine.py` + `__init__.py`; сохранился только в отдельном репо `adaptive-learning-repetitor`).
Вместо него в живом чате реально работает `adaptive/engine.py::decide()` — импортируется `chat/graph.py` (`adaptive_decide`) и `chat/rag_router.py`, то есть это не мёртвый код, а часть узла `classify` в реальном графе LangGraph. Что он умеет:
  - `PREREQUISITES`-словарь + `_find_unmastered_prerequisite`: если accuracy<50% после ≥3 попыток — форсирует возврат к первому непройденному пресквизиту вместо продолжения (Rule 1);
  - выбор самой слабой готовой темы через `_pick_weakest` (по `als_score`);
  - подстройку сложности (5 правил приоритета) с учётом calibration (over/underconfident nudge).
Это **не топологическая сортировка по всему графу тем** (как ожидал бы «Curriculum Planner» в классическом смысле — построение целого упорядоченного силлабуса), а реактивное, потурновое решение «что делать дальше с одной темой». Для текущего охвата Anki Lite (словарь + грамматический чат) это и есть работающий эквивалент планировщика — писать topological-sort curriculum.py с нуля означало бы новую фичу, а не починку существующей.

### Task 7.5 — End-to-end core check

**Goal:** связка работает целиком: ответ студента → событие → BKT → mastery → SRS-очередь → планировщик.
**Steps:**
1. Прогнать реальную сессию: несколько ответов, проверить, что данные проходят всю цепочку.
2. Убедиться, что learning events реально доходят до BKT (если публикация асинхронная — что очередь не теряет события).
**Acceptance:**
- [x] Ответ в тренировке приводит к обновлению mastery в БД.
- [ ] Изменённый mastery влияет на следующую выдачу (очередь/планировщик). **← НЕ подтверждено для основной SRS-очереди слов, см. статус**
- [ ] Integration-тест на полную цепочку.
- [x] **Статус каждого компонента записан в этот файл.**

**Статус (2026-07-23): цепочка полностью прослежена — это ДВА независимых контура, а не один замкнутый цикл.** Ключевая находка Epic 7.

1. **SRS-контур слов (основной цикл Anki Lite):** Go `SubmitReview` → `nextLevelState` → запись в `ankis-db` → следующий вызов `NextReviewWord`/`SelectSessionWords` читает те же таблицы. Полностью самодостаточен, Python вообще не участвует в планировании — работает.
2. **Mastery/BKT-контур (для чат-AI):** тот же ответ дополнительно кладётся в outbox → `RunEventPublisher` реле́ит по gRPC → `publish_event` → `TopicMasteryRepository.update_from_event` обновляет BKT+ALS в llm-db → при следующем чтении (`get_by_project`, с применённым forgetting-распадом) это видят `adaptive/engine.py::decide()` и weak-topics tool чата.

**Эти два контура запускаются одним и тем же событием (ответ на карточку), но не образуют один замкнутый adaptive loop**: обновлённый BKT-mastery влияет на поведение чат-ассистента (какую тему предложить, weak-topics-репорт), но **никогда не влияет на то, какая карточка станет следующей в основном экране повторения слов** — там нет ни одного вызова к llm-service. Если тезис «адаптивное ядро» подразумевает, что SRS-расписание само подстраивается под BKT-mastery — это утверждение **не подтверждается кодом**: на деле это два раздельных адаптивных механизма, использующих общий входной сигнал, а не единую петлю.

Дополнительно (надёжность контура 2): retry outbox ограничен `publish_attempts < 10` ([repository.go:614](back/internal/storage/repository.go#L614), [event_publisher.go:15](back/internal/service/event_publisher.go#L15)); после 10 неудачных попыток строка навсегда перестаёт выбираться, без алертинга — при длительной недоступности `llm-service` часть learning-событий для mastery/chat молча теряется навсегда (SRS-состояние слова при этом не страдает — оно уже сохранено синхронно до постановки в outbox).

**Что нужно чинить/уточнить, если "адаптивное ядро влияет на SRS" — часть тезиса защиты:**
- Либо явно переформулировать тезис (два контура: SRS для слов + BKT-driven чат-ассистент, независимые по дизайну), либо
- Добавить реальную связь: например, `NextReviewWord`/`SelectSessionWords` могли бы приоритизировать слова с низким `als_score`/`mastery_score` из llm-db — этого сейчас нет, потребует нового gRPC-вызова (`GetWeakTopics` уже существует в контракте, но Go его вызывает не оттуда).

**Не хватает:** integration-теста на полную цепочку (ни для контура 1, ни для контура 2 не найдено).

## EPIC 8 — AI Latency Optimization (P1)

> Ускорить ответ AI-помощника. Цель — снизить время до первого токена и полное время ответа. Сначала измерить, потом оптимизировать точечно (не наугад).

### Task 8.1 — Measure current latency

**Goal:** понять, где именно уходит время.
**Steps:**
1. Инструментировать пайплайн таймерами по этапам: `classify` → `route/retrieve` → `call_model` (до первого токена) → полный ответ.
2. Прогнать 20–30 типовых запросов, собрать среднее и медиану по каждому этапу.
3. Определить бутылочное горлышко (обычно это либо retrieval, либо латентность LLM).
**Acceptance:**
- [ ] Есть разбивка времени по этапам (числа, не ощущения).
- [ ] Названо главное узкое место.

### Task 8.2 — Optimize the bottleneck

**Goal:** ускорить найденный этап. Кандидаты (применять по результатам 8.1):

**Если медленный retrieval:**
- [ ] Проверить HNSW-индекс: параметры `ef_search`, наличие индекса на нужных колонках.
- [ ] Кэшировать эмбеддинг частых запросов (Redis).
- [ ] Ограничить top-k разумным числом.
- [ ] Убедиться, что эмбеддинг-модель загружена в память один раз, а не на каждый запрос.

**Если медленный classify (лишний LLM-вызов):**
- [ ] Рассмотреть более лёгкую/быструю модель для классификатора.
- [ ] Кэшировать классификацию повторяющихся формулировок.
- [ ] Проверить, нельзя ли объединить classify и route в один вызов.

**Если медленный call_model (латентность LLM):**
- [ ] Убедиться, что стриминг включён (первый токен важнее полного ответа).
- [ ] Проверить размер контекста — не раздут ли промпт лишними документами.
- [ ] Сократить top-k передаваемых в LLM фрагментов до релевантных.
- [ ] Проверить регион/эндпоинт LLM-провайдера (VseLLM latency — 0.71с у gemini-flash).

**Общее:**
- [ ] Параллелить независимые шаги, где возможно (например, retrieval из нескольких корпусов одновременно при ensemble).

**Acceptance:**
- [ ] Время узкого места измеримо снизилось (до/после в числах).
- [ ] Полное время ответа улучшилось, качество (Faithfulness/Recall) не просело.
- [ ] Результаты записаны в этот файл.

### Task 8.3 — Verify no quality regression

**Goal:** ускорение не сломало качество.
**Steps:**
1. Прогнать eval-датасет до и после оптимизации.
2. Сравнить Router Accuracy, Recall@5, Faithfulness.
**Acceptance:**
- [ ] Метрики качества не упали относительно baseline.
